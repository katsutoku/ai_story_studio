# AI Story Studio

小説・ノベルゲーム・アドベンチャーゲームのシナリオ制作を支援するWebアプリケーション（Flask版・雛形）。

仕様書「AI Story Studio 仕様概要書」に基づき、以下の情報管理機能を実装しています。

- プロジェクト（作品）管理
- キャラクター管理
- 世界設定管理
- 章管理（本文はMarkdownファイルとして保存）
- 伏線管理（pending / processing / completed / failed）
- **AIシナリオ生成（マルチプロバイダ対応）**：ChatGPT（OpenAI）/ Gemini（Google）/ Claude（Anthropic）/ Ollama（ローカル実行）から生成時に選択可能。作品情報・キャラクター・世界設定・過去章要約・未回収の伏線をプロンプトに含めて次章を自動生成
- **AIキャラクター生成**：作品情報（タイトル・ジャンル・あらすじ）と既存のキャラクター・世界設定をもとに、AIが新規キャラクター案をJSON形式で複数提案。プレビュー画面で内容を確認し、登録したいものだけ選んでDBに保存できる（未保存の下書き段階を挟むため、気に入らない案はそのまま破棄できる）
- **AI世界設定生成**：キャラクター生成と同じ設計で、世界観の案を複数提案・プレビュー・選択登録できる
- **AI伏線生成**：既存の章一覧を踏まえて配置章・回収章の候補も自動で対応付け。該当する章がない場合は未設定のまま登録され、後で手動編集できる
- **おまかせ生成モード（全体プロット一括生成）**：作品タイトル・ジャンル・あらすじと大まかな要望だけから、AIがキャラクター・世界設定・全章の設計図（本文はまだ書かない、タイトル・要約・目的のみ）・伏線をすべて連動させて一括提案。プレビュー画面で確認して選択登録した後は、章一覧から通常の章生成フローで1章ずつ本文を執筆する（本文生成時は、あらかじめ登録された「その章の設計図」と「今後の章の予定」が自動的にプロンプトへ反映されるため、行き当たりばったりにならず全体の伏線・展開と整合した本文が書かれる）

## セットアップ

```bash
python -m venv venv
source venv/bin/activate   # Windowsは venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# .env を編集し、SECRET_KEY と使用したいAIプロバイダのAPIキーを設定する

python run.py
```

起動後、ブラウザで `http://127.0.0.1:5000/` にアクセスしてください。

## 実装済みのエラーハンドリング

- 存在しないデータへのアクセス → 404エラー画面
- 章本文のMarkdownファイルが存在しない場合 → 空文字として編集画面を表示
- 必須項目未入力（タイトル・章番号・キャラクター名・プロジェクト名）→ 保存せず入力画面へ戻す
- 本文ファイル保存失敗時 → DB更新を中止しエラーメッセージを表示
- AI生成失敗時（認証エラー・通信エラー・レート制限など）→ 章の生成ステータスを`failed`に更新し、エラーメッセージを表示し、再生成可能な状態にする

## AIシナリオ生成機能の使い方

1. `.env` に、使用したいAIプロバイダのAPIキーを設定する
   - ChatGPT: `OPENAI_API_KEY`（https://platform.openai.com/api-keys ）
   - Gemini: `GEMINI_API_KEY`（https://aistudio.google.com/apikey ）
   - Claude: `ANTHROPIC_API_KEY`（https://console.anthropic.com/settings/keys ）
   - Ollama: APIキー不要。ローカルで `ollama serve` を起動し、`OLLAMA_BASE_URL`（デフォルト `http://localhost:11434`）と
     `OLLAMA_MODEL`（例: `llama3.1`）を指定する
2. `DEFAULT_AI_PROVIDER` で生成画面を開いたときに最初に選択されるプロバイダを指定できる（省略時は`gemini`）
3. 作品詳細画面、または章一覧画面の「AIで次章生成」ボタンから生成画面へ
4. 章番号（自動的に次の番号が入力される）・仮タイトル・**利用するAI（プルダウン）**・追加指示（任意）を入力して生成
5. 生成された本文は自動的にMarkdownファイルとして保存され、本文編集画面へ遷移する
6. 生成に失敗した場合は章一覧に「再生成」ボタンが表示され、別のAIプロバイダに切り替えて再試行することもできる

内部的には `app/ai_service.py` の `build_prompt()` が、作品情報・キャラクター・世界設定・
これまでの章の要約・未回収の伏線（`Foreshadowing.status == "pending"`）を
共通のプロンプトとして組み立て、選択されたプロバイダに応じて
`_generate_with_openai()` / `_generate_with_gemini()` / `_generate_with_claude()` / `_generate_with_ollama()`
のいずれかに振り分けている。どの章がどのAIで生成されたかは `Chapter.generation_provider` に記録される。

### 章構成の方針（常に適用される）

`build_prompt()` は、追加指示の有無にかかわらず常に次の方針をAIへ指示する。

- 各章は、それ単体で起承転結が完結する小さな事件・エピソードとして書く（「逆転裁判」のような話数完結型のイメージ）
- 同時に、その章の中に最終章で明かされる大きな謎につながる手がかりを、読者に今は気づかせない程度にさりげなく仕込む

この方針を章ごとに変えたい場合は、生成画面の「追加指示」欄で上書き・補足する。

### セリフのト書き表記（常に適用される）

ゲーム用シナリオスクリプトへの変換を見据え、本文中のセリフ行は必ず次の形式で書かれる。

```
【高橋健】「本当にここでいいのか？」
```

- 発言者名を行頭に`【】`で囲んで明記し、直後にセリフを`「」`で書く
- 発言者名は常に実名で表記する

「正体を隠したいキャラクターは？？？のように表記する」という案も検討したが、正体の開示タイミングは
ゲームのシナリオシステム側でフラグ管理するか、人が手を入れて調整する領域と考え、見送った。

### 場面情報の記載（常に適用される。本文の一番先頭）

背景画像の自動判別を見据え、本文の一番先頭には必ず次の2行が入る。

```
■背景:岸壁
■場面:深夜の岸壁
```

- **`■背景:`**：背景画像の判別に使う短い場所名（例：岸壁、教室、駅前）。時間帯や状況の修飾語は含めない。
  同じ物理的な場所は章をまたいでも表記を統一するよう指示しているため、背景画像アセットを使い回しやすい。
  世界設定に地名が登録されている場合は、それを優先して使うよう指示している。
- **`■場面:`**：時間帯や状況を含めた、内容から推測される場面の呼び名（例：深夜の岸壁）。
  表示・参考用の情報で、背景画像の判別には使わない。

この2行は、章の新規生成・再生成だけでなく、「本文のAIによる部分修正」でも維持・更新されるよう
指示している（修正によって場所や時間帯が変わった場合は、この2行も合わせて書き換えさせる）。

1つの章の中で場面（場所や時間帯）が転換する場合は、その都度、切り替わった直後の文章ブロックの
先頭にも同じ形式で■背景:・■場面:の2行を挿入するよう指示している。そのため、1章の中に複数の
場所が登場する構成でも、`^■背景:(.+)$`のような正規表現で章内の全ての場面転換箇所を機械的に
検出できる。

### 1回のAI呼び出しの出力上限（章の分量調整）

`.env`の`AI_MAX_OUTPUT_TOKENS`（デフォルト: 8192）で、1回のAI呼び出しが生成できる最大トークン数を
4プロバイダ共通で調整できる。1章あたりの分量を増やしたい場合はこの値を大きくする。

```
AI_MAX_OUTPUT_TOKENS=20000
```

- 日本語はおおよそ1トークン≒1〜2文字なので、20000トークンで1万〜2万字程度が目安（モデルにより変動する）
- モデル・プロバイダ側にも上限があるため、大きくしすぎるとエラーになることがある。利用モデルの仕様を確認すること
- 「逆転裁判」のような1話が長編になる構成を作る場合、この値を上げるだけでは限界があるため、
  1つのエピソードを複数の章（例：「第1章-1：捜査編」「第1章-2：法廷1日目」）に分けて生成する運用と
  組み合わせることを推奨する

## AIキャラクター/世界設定/伏線生成機能の使い方

1. 各管理画面（キャラクター管理・世界設定管理・伏線管理）の「AIでたたき台を生成」ボタンから生成画面へ
2. 生成する件数（1〜10件）・利用するAI・追加指示（任意）を入力して生成
3. プレビュー画面で候補が表示される（この時点ではまだDBに保存されていない）
4. 登録したいものだけチェックを入れて「登録する」を押すと保存される
5. 登録後は通常の編集画面から個別に内容を調整できる

章生成とは異なり、生成結果を確認してから選んで保存する一段階を挟んでいる点が特徴。
不要な候補はチェックを外すか、そのままプレビュー画面を離れれば破棄される（DBには一切残らない）。

伏線生成のみ、AIが提案した配置章・回収章の「章番号」を既存の章と照合し、
一致する章があれば自動的に紐付ける。該当する章がない場合（まだ章を登録していない、
AIが存在しない章番号を答えた等）は未設定のまま登録されるので、必要に応じて後から編集する。

### キャラクター名の重複防止

キャラクター名は、同一作品内でユニークになるようにしている（前後の空白・大文字小文字の違いは無視して比較する）。

- **新規登録**：同名のキャラクターが既にいる場合、確認なしでは保存されない。警告とともに、
  「この内容で既存のキャラクターを更新する」ボタンが表示され、新規作成ではなく既存レコードの
  上書き更新として保存できる（別の名前を付けて登録し直すことも、名前を変えればもちろん可能）。
- **編集（改名）**：改名先の名前が、別の既存キャラクターと重複する場合は保存をブロックし、
  警告を表示する（2つのキャラクターが同じ名前になってしまうことを防ぐ）。
- **AIによるキャラクター一括生成**：登録時に、既存のキャラクターと同名の候補、および
  今回選択した候補同士で名前が重複しているものは自動的にスキップされる（生成のたびに手動で
  気づいて弾く必要がない）。スキップされた名前は登録完了時のメッセージで一覧表示される。

## おまかせ生成モードの使い方

漫画雑誌の編集担当のように、大まかな要望だけをAI作家に伝えてすべて任せたい場合の使い方。

1. 作品詳細画面の「AIで全体プロットを生成」ボタンから生成画面へ
2. 章数（1〜20章）・利用するAI・作品への大まかな要望（任意）を入力して生成
3. プレビュー画面に、キャラクター・世界設定・全章の設計図（タイトル・要約・目的のみ、本文はまだなし）・
   伏線がまとめて表示される（この時点ではまだDBに保存されていない）
4. 登録したいものだけチェックを入れて「登録する」を押すと保存される
5. 章一覧画面に、本文がまだ空の章がずらっと並ぶので、確認しながら1章ずつ「AIで次章生成」または
   「再生成」ボタンで本文を執筆していく

本文生成時（手順5）は、その章のためにあらかじめ登録された要約・目的、および今後の章の予定が
自動的にプロンプトへ組み込まれるため、行き当たりばったりの生成にならず、全体プロットに沿った
一貫性のある本文が書かれる。この一括生成は章数が多いとAPI呼び出しが多く時間がかかるため、
本文の一括自動生成はあえて行わず、章単位で確認しながら進める設計にしている。

## 禁止事項・既知の事実欄の使い方

ミステリー作品などで「特定の展開を悟らせたくない」「時系列上の矛盾を防ぎたい」場合に使う機能。

1. 作品情報の編集画面（`projects.edit`）に「禁止事項・既知の事実」欄がある
2. ここに書いた内容は、章の本文生成・全体プロット生成・キャラクター生成・世界設定生成・伏線生成の
   **すべてのAI呼び出しで毎回自動的にプロンプトへ差し込まれる**
3. 例：
   - 「主人公が真犯人であることは最終章まで読者に悟らせないこと」（書いてほしくない方向性の抑制）
   - 「被害者Aの死亡推定時刻は22時。主人公はその時刻は駅前の喫茶店にいたことにする」（動かせない事実の固定）

一度書けば以後の生成すべてに効くので、章を生成するたびに同じ注意書きを追加指示欄に手打ちする必要がなくなる。
ただしAIによる生成である以上、完全に矛盾がゼロになる保証はないため、生成後は本文を確認する運用が引き続き重要。

## 本文のAIによる部分修正

一度生成した本文の一部だけを直したい場合（「被害者を別のキャラにしたい」「会うのを前日に変更したい」など）に使う機能。
「再生成」がゼロから本文を書き直すのに対し、こちらは**既存の本文をAIに読ませた上で、指示した変更点だけを反映**させる。

1. 章一覧の「AIで部分修正」ボタン（本文が生成済みの章にのみ表示される）から修正画面へ
2. 修正指示（例：「被害者を〇〇から△△に変更してください」）と利用するAIを入力して「修正する」
3. 修正前・修正後を見比べられるプレビュー画面が表示される（この時点ではまだファイルは上書きされていない）
4. 修正後の本文はプレビュー画面でそのまま編集もできる。内容を確認して「この内容で保存する」を押すと、
   Markdownファイルが上書きされる

**注意**：修正対象の章より後の章がすでに生成済みの場合、その章が旧設定を前提にした記述を含んでいると、
この修正によって新たな矛盾が生まれる可能性がある。後続の章がある場合は、あわせて見直すことを推奨する
（これは自動検知できないため、運用上の注意点として留意する）。

### 改行コードの正規化

ブラウザは`<textarea>`の内容を送信する際、内部の改行(`\n`)をすべて`\r\n`（CRLF）に変換して送信する。
これを正規化せずに保存すると、本文編集・AI生成・部分修正の保存を繰り返すたびに`\r`が本文に蓄積し、
表示環境によっては余分な改行に見えてしまう。これを防ぐため、`app/routes/chapters.py`の
`_normalize_newlines()`が、Markdownファイルへの書き込み・読み込みのすべての箇所で
改行コードを`\n`に統一している。

## その他の細かい機能

### 尋問シナリオ生成（探偵役・容疑者役の独立セッション方式）

逆転裁判のような、探偵・刑事が容疑者を尋問する応酬シーンを生成する機能。章一覧の
「尋問シナリオ生成」ボタンから使う。

**課題と設計方針**：通常の章生成は1回のAI呼び出しで全キャラクターのセリフを含む本文を
書かせるため、AIが全員の秘密を知った状態で書いてしまい、本来知らないはずの情報が
会話に漏れる（矛盾を生む）リスクがある。この機能では、**探偵役と容疑者役を完全に別々の
AI呼び出しとして実行**し、以下のルールで情報を渡すことでこれを防いでいる。

- **探偵役のプロンプトには、`Project.constraints`（真相・犯人などの秘密情報）を一切含めない**。
  公開情報（画面で入力する`public_context`）とこれまでの会話だけから、次の質問を考えさせる。
  これにより「探偵が最初から答えを知っている」状態を防ぐ
- **容疑者役のプロンプトには、その容疑者専用の秘密（`suspect_secret`）と`Project.constraints`を渡す**。
  他の容疑者の秘密は一切渡さない
- 探偵の発言→容疑者の返答、を1ターンとして交互に呼び出しを繰り返す（3〜20ターンで指定可能）。
  1ターンごとに1〜2文の短いセリフを生成し、`【名前】「セリフ」`の書式で連結していく

**容疑者の秘密はDBに保存されない**。生成のたびに画面上で入力する一時的な情報として扱う
（通常の章生成プロンプトに紛れ込んで漏洩することを防ぐため）。

生成結果はプレビュー画面で確認でき、既存の章本文への「追記」または「上書き」を選んでから
保存する（他の生成機能と同様、確認なしに即保存はしない）。

**現状の制約**：容疑者は1回のセッションにつき1人のみ（複数人を尋問したい場合は、この機能を
容疑者ごとに複数回実行する運用）。プレイヤーが選択肢を選ぶ・証拠品を提示するような
インタラクティブな分岐生成には対応していない（これは「シナリオ分岐エンジン」全体の話として
別途保留にしている。完成した1本道の尋問シナリオを土台に、後から分岐ポイントを追加生成する
という2段階のアプローチを検討中）。矛盾の自動検知（判定AI）は当時は見送ったが、後述の
「ミステリー・トリック生成モジュール」のPhase5として実装済み（本文だけでなく、この尋問
シナリオの出力も検証対象にできる）。

### ミステリー・トリック生成モジュール（事件のトリック・配役・環境・矛盾検知）

事件（謎解き）のあるシナリオ向けに、トリック（真相）・矛盾セット・現場の状況証拠を段階的に
AIに考えさせ、最後に実際の本文と正解データを突き合わせて矛盾を検出する一連の機能。
プロジェクト詳細画面の「事件」セクション、または各プロジェクトの `/mystery-cases/` から使う。

- **Phase1（構想）**：事件名・世界観の補足・オチ（絶対条件）を入力する。オチは任意入力で、
  空欄のまま次のPhase2に進むと、オチ自体もAIが考案し、トリック確定時に自動で書き戻される。
  「探偵役はこのキャラクターに固定したい」のような強い希望がある役割だけ、
  `役割: キャラクター名`の形式で任意入力できる（例：`detective: 名探偵コナン`）。
  それ以外の役割・人数はAIに委ねる。
- **Phase2（トリック生成）**：オチと世界観から、真相の仕組み・ミスディレクション・矛盾セット
  （プレイヤーが証拠を突きつけて破綻させられるポイント）・必要な役割の一覧（抽象配役表）を
  AIが考える。この時点では役割はまだ「探偵」「目撃者」のような抽象的な状態。
- **Phase2.5（配役）**：抽象配役表の各役割に、既存キャラクターを選ぶか、AIにその場で
  「事件専用のモブキャラ」を生成させて割り当てる。モブキャラは`Character`にひもづくが、
  メインのキャラクター管理一覧には表示されず、事件詳細画面からのみ確認・管理できる。
- **Phase3（環境・小道具生成）**：全ての役割の配役が完了すると、確定したトリックと配役済みの
  実名一覧をもとに、矛盾のない現場のタイムライン・場所・天候・小道具をAIが生成する。生成中に
  新たな役割（例：見張り役がもう1人）が必要と判明した場合は、自動的に配役ステップへ差し戻される。
- **Phase5（矛盾検知）**：事件の正解データ（トリック・環境）と、実際に書かれた章本文、または
  尋問シナリオのログ（直接貼り付け）を比較し、キャラが知るはずのない情報を話していないか、
  タイムラインとの矛盾はないか等をAIが検証する。ボタンを押したときだけ実行され、章生成のたびに
  自動実行されることはない。

**秘匿情報の扱い（最重要）**：真相（トリックの仕組み）は、通常の章生成プロンプトには
自動では一切渡されない。事件が発生する章の範囲（`trigger_chapter_id`〜`resolution_chapter_id`。
事件詳細画面の「章との紐付け」で設定）の中でだけ、以下の2段階のオプトインで注入できる。

- 事件範囲内の章では、その事件専用のモブキャラだけは自動的にキャラクター一覧に加わる
  （範囲外の章では存在しないものとして扱われる）
- 章生成フォームで明示的にチェックした場合のみ、環境データ（客観的事実。真相そのものではない）
  が注入される（デフォルトOFF）
- 「解決編」として紐付けた章で、かつ章生成フォームでさらに別途チェックした場合のみ、
  真相そのものが注入される（デフォルトOFF。二重のオプトインを要求している）

なお、この機能は当初「トリック提案AI・構造化難事件データベース（RAG）」として一度見送られた
経緯がある。今回は方針転換し、過去事件のベクトル検索・類似トリック検索DBは作らずに
（AIの一般知識＋厳格なJSONスキーマ＋Phase5の事後検証に任せる）、トリック提案AI自体だけを
本体機能として復活させている。

#### お任せモード（Phase2〜Phase3の一括生成）

事件詳細画面で、まだトリックを生成していない事件（構想中の状態）にのみ「AIにすべてお任せして
生成する」ボタンが表示される。押すと、トリック生成（Phase2）→配役（Phase2.5）→環境・小道具
生成（Phase3）を、プロバイダを選ぶだけの1回の操作でまとめて実行する。

- 配役は、Phase1の「固定配役の希望」で指定した役割はそのまま使い、それ以外の役割はすべて
  AIが生成した事件専用のモブキャラを1件ずつ自動的に採用する（既存キャラクターからの手動選択は
  行わない。既存キャラを関わらせたい場合は、事前にPhase1の固定配役の希望で指定しておく）
- 生成の途中（トリックだけ成功、配役の途中で失敗、など）で何かが失敗した場合、それまでの
  結果はDBに一切保存されない。エラー内容がflashメッセージで表示され、個別のフロー
  （トリック生成→配役→環境生成）でやり直すこともできる
- すべてのフェーズが成功すると、トリック・配役結果・環境データを1画面にまとめたプレビュー
  （真相はデフォルト非表示のネタバレトグル付き）が表示され、確定ボタンを押した時点で
  初めてまとめてDBに保存される（他の生成機能と同じ「生成→プレビュー→選択保存」パターン）
- 環境生成の過程で追加の役割が必要と判明した場合、お任せモードではその役割を自動反映しない
  （保存後にflashで警告し、配役画面から手動での対応を促す）

### キャラクターのサムネイル画像

キャラクター編集画面から、jpg/png/gif/webp形式の画像（5MBまで）をアップロードできる。

ファイルを選択すると、保存前でもその場でプレビューが表示される（JavaScriptの`FileReader`で
選択直後にブラウザ内だけで表示しており、この時点ではまだサーバーには送信されない）。
新規登録画面でも、保存する前に選んだ画像を確認できる。

- 保存先はサーバー側のローカルディスク（`.env`の`CHARACTER_THUMBNAIL_DIR`、デフォルト`data/character_thumbnails`）。
  章本文のMarkdownファイルと同じ考え方で、DBにはファイル名のみを保持し、実体はファイルシステムに置く
- 画像は`/projects/<id>/characters/<id>/thumbnail`から配信される。DBにファイルパスをそのまま持たせず、
  必ずこのURL経由でアクセスさせることで、将来的に保存先をクラウドストレージ等に変更する場合も、
  DBスキーマや呼び出し側のURLを変えずに配信ルートの中身だけ差し替えれば対応できる
- 新しい画像をアップロードすると、古いファイルは自動的に削除される。「サムネイル画像を削除する」
  チェックボックスで画像なしの状態にも戻せる。キャラクター自体を削除した場合も、紐づく画像ファイルは
  あわせて削除される

**注意**：この方式は、アプリを1台のサーバー（またはクラウド上の1箇所）に集約してホスティングする
運用を前提にしている。チームの各メンバーがそれぞれ自分のPCでアプリを起動する運用のままだと、
画像を登録した人のPC上にしかファイルが存在せず、他のメンバーからは見えない点に注意すること。
チームでの共有を重視する場合は、将来的にクラウドのオブジェクトストレージ（S3、Cloudflare R2等）に
保存先を差し替えることを検討する（`_save_thumbnail_file`/`_delete_thumbnail_file`/配信ルートの
3箇所を、対象のストレージサービスのAPI呼び出しに置き換えることで対応できる見込み）。

### 人物相関図

制作者がストーリー全体の人物相関を俯瞰するための補助機能。作品詳細画面の「相関図」ボタン、または
キャラクター一覧画面から遷移できる。

1. 利用するAI・追加指示（任意）を入力して生成
2. 登録済みのキャラクター・世界設定・章の要約・伏線をもとに、AIが人物同士の関係性を
   `[{"from", "to", "relationship"}, ...]`のJSON形式で提案する
3. `app/diagram_utils.py`が、このJSONデータをvis-network（vis.js）用のノード/エッジデータに
   機械的に変換する（AIに直接図の記法まで書かせると文法ミスで図が壊れることがあるため、
   「データ生成はAI、描画用データへの変換はコード」という役割分担にしている）
4. ブラウザ側でvis-network（CDN経由）が実際の図として描画する。ノードはドラッグして
   自由に配置し直せる（レイアウトを操作できる）

AIが返した人物名が、登録済みキャラクターの名前と一致し、かつサムネイル画像が設定されている場合は、
そのノードを円形の顔写真（`circularImage`）として表示する。一致しない場合（世界設定や未登録の
人物など）は通常の四角いボックスのまま表示される。キャンバスは`aspect-ratio: 1 / 1`のCSSで
正方形に固定しており、幅に応じて高さも追従する（最大900px）。

**キャッシュとAI呼び出しの最小化**：生成結果は`Project.relationship_diagram_json`に保存され、
次回以降は`/projects/<id>/relationships/`にアクセスしてもAIを呼ばずキャッシュを表示する。
キャラクター・世界設定・章・伏線のいずれかが、相関図の生成日時より後に更新されていた場合は
「内容が更新されています」という案内を表示するが、**AIの再呼び出しは利用者が「更新する」ボタンを
押したときのみ**（ページを開くたびに自動でAPIが呼ばれることはない）。

なお、作品情報（タイトル・ジャンル・あらすじ・禁止事項欄）自体を直接編集した場合の更新検知は
対象外にしている。理由は、相関図データもProjectテーブルの列であるため、Project自体の`updated_at`を
比較対象に含めると、相関図を保存した直後に「自分自身の更新」を「内容が古くなった」と誤検知して
しまうため（`app/routes/relationships.py`の`_content_last_updated_at()`にコメントで詳細を記載）。

将来的に「事件・伏線も含めた関係図」に拡張する場合も、ノードの対象を`Character`だけでなく
`Chapter`・`Foreshadowing`にも広げる形で、同じ設計のまま対応できる見込み。

- **章一覧・伏線一覧の「すべて削除」**：全体プロットを再生成する前に、既存の章・伏線をまとめて削除できる。
  章を削除すると、その章を参照している伏線の配置章・回収章は自動的に「未設定」に戻る（データの不整合を防ぐため）。
  キャラクター・世界設定・作品情報はそのまま残るので、「キャラや世界観は気に入っているが、章と伏線だけ作り直したい」
  という場合は、この一括削除→全体プロット再生成（キャラクター・世界設定のチェックは外す）という流れで対応できる。
- **AI生成中インジケーター**：章・キャラクター・世界設定・伏線・全体プロットの各生成ボタンを押すと、
  生成が完了するまで画面全体にローディング表示が出る（二重送信の防止も兼ねる）。

### エラーログ

AI生成に失敗した場合、利用者にはflashメッセージでエラー内容を表示するのに加え、サーバー側にも
記録を残す。保存先はサーバー側のローカルディスク（`.env`の`LOG_DIR`、デフォルト`data/logs/app.log`、
1MBごとにローテーションし直近3世代を保持）で、いつ・どの作品/章/事件で・どんなエラーが起きたかを
トレースバック付きで確認できる。AI生成以外の予期しないエラー（500エラー）も、Flaskの標準動作により
同じログファイルに記録される。
